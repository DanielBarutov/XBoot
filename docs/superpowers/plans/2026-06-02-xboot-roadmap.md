# XBoot v1 — Дорожная карта (фазы 01–08)

**Дата:** 2026-06-02
**Спека:** `docs/superpowers/specs/2026-06-02-xboot-diskless-boot-engine-design.md`
**Статус:** утверждена; имплементационные планы пишутся по одной фазе за раз.

## Как читать этот документ

Это **дорожная карта**, а не имплементационный план. Она делит работу v1 на 8 фаз,
упорядоченных по зависимостям. Каждая фаза — самостоятельный кусок, который:
- даёт работающий, тестируемый результат;
- получит **отдельный имплементационный план** (`docs/superpowers/plans/2026-..-phaseNN-*.md`)
  с пошаговыми TDD-задачами — пишется непосредственно перед стартом фазы.

Порядок строгий: каждая следующая фаза опирается на предыдущую. Игровой диск не выделен
в отдельную фазу — он переиспользует тот же COW/кэш/iSCSI-движок и добавляется как
дополнительный LUN в фазах 05 и 07.

### Граф зависимостей

```
01 Скаффолд
   └─► 02 Backing stores ─► 03 COW Volume ─► 04 Block Cache ─┐
                                                             ├─► 05 iSCSI Target ─┐
                              06 Сетевая загрузка ───────────┘                    │
                              (зависит только от 01)                              │
                                                                                  ▼
                                                            07 Сборка + Disk/Client Manager
                                                                                  │
                                                                                  ▼
                                                            08 E2E на Windows + закалка
```

Фаза 06 (сеть) зависит только от 01, поэтому может идти параллельно с 02–05, если будет
вторая пара рук. По умолчанию делаем последовательно 01→08.

## Фаза 01 — Скаффолд и фундамент

**Цель:** рабочий каркас проекта, в который дальше встраиваются подсистемы.

**Объём:**
- Cargo-проект (рассмотреть workspace: `xboot-core` библиотека + `xboot` бинарник).
- tokio как async-рантайм; выбрать и подключить логирование (`tracing`).
- Парсинг TOML-конфига в типизированную модель: `Disk { id, type, backing, mode, ram_cache, policy }`,
  `Client { mac, name, system, games, writeback }`, `client_defaults`.
- Валидация конфига: ссылки клиента на диски существуют, типы дисков совпадают с ролью
  (system → image, games → game, writeback → writeback).
- Заглушки трейтов `BackingStore` и `NetIo` (сигнатуры, без реализаций).
- CI: сборка, `cargo test`, `cargo clippy --all-targets`, `cargo fmt --check`.

**Зависимости:** нет.

**Тестирование:** юнит-тесты на парсинг и валидацию конфига (валидные + битые конфиги
дают понятные ошибки).

**Готово, когда:** бинарник принимает путь к конфигу, парсит его, печатает разобранную
модель или внятную ошибку валидации; CI зелёный.

---

## Фаза 02 — Backing stores (форматы образов)

**Цель:** уметь читать блоки из образов разных форматов через единый трейт.

**Объём:**
- Реализации `BackingStore` (read): raw-файл, **fixed VHD**, **dynamic VHD**, **VHDX**.
- Разбор структур: VHD footer; dynamic VHD — BAT и блоки; VHDX — header/region/BAT/metadata.
- Чтение по смещению/блоку с корректной трансляцией «виртуальный сектор → физическое смещение».
- (Запись в мастер не нужна — мастер только на чтение. Запись пойдёт в оверлей, фаза 03.)

**Зависимости:** 01 (трейт `BackingStore`).

**Тестирование:**
- Юнит-тесты на каждый формат с маленькими заранее заготовленными фикстурами.
- `proptest`: чтение случайных смещений из dynamic-образа == чтение из эталонного raw той же
  «болванки».
- `cargo-fuzz` на парсерах VHD/VHDX: мусор на входе → ошибка, не паника/крэш.

**Готово, когда:** все четыре формата читаются корректно на фикстурах; property-тесты и
фаззер зелёные.

---

## Фаза 03 — COW Volume Manager

**Цель:** виртуальный том клиента = read-only мастер + volatile writeback-оверлей с copy-on-write.

**Объём:**
- Тип `Volume`, собирающий RO `BackingStore` + per-client оверлей.
- Оверлей: хранит, какие блоки были перезаписаны клиентом, и сами данные (на writeback-диске
  и/или в RAM — детали в имплементационном плане).
- READ: оверлей → мастер (см. правило COW в спеке §4).
- WRITE: всегда в оверлей; мастер физически не трогаем.
- Сброс оверлея (volatile): создание/уничтожение оверлея на сессию.

**Зависимости:** 02 (есть откуда читать мастер).

**Тестирование:**
- Юнит-тесты на все ветки READ/WRITE.
- `proptest`: случайная последовательность READ/WRITE на `Volume` даёт ровно тот же результат,
  что эталонная in-memory модель (массив байт). Это математически фиксирует корректность COW.
- Тест жизненного цикла: запись → «ребут» (сброс оверлея) → чтение возвращает мастер.

**Готово, когда:** мастер доказуемо неизменен, запись изолирована в оверлее, сброс работает;
property-инвариант COW зелёный.

## Фаза 04 — Block Cache (общий RAM-кэш)

**Цель:** один раз держать в RAM горячие блоки мастера на всех клиентов; не превышать бюджет.

**Объём:**
- Кэш блоков read-only мастер-образов, встраивается между `Volume` и `BackingStore`.
- Бюджет RAM **на диск** (`ram_cache` из конфига); LRU-вытеснение в пределах бюджета.
- Кэш общий для всех клиентов одного мастера (они читают одинаковые блоки).
- Потокобезопасность (несколько клиентов читают конкурентно).

**Зависимости:** 02 (источник блоков), 03 (точка встраивания на пути чтения).

**Тестирование:**
- Юнит-тесты: hit/miss, LRU-порядок, граничные размеры бюджета, заполнение и вытеснение.
- Тест: общий объём кэша диска никогда не превышает `ram_cache`.
- Конкурентный тест: параллельные чтения одного мастера не портят кэш (под санитайзером).

**Готово, когда:** повторные чтения обслуживаются из кэша, бюджет соблюдается, LRU корректен
под нагрузкой.

---

## Фаза 05 — iSCSI Target

**Цель:** реальный iSCSI-инициатор может подключиться и работать с томом клиента.

> **Нарезка (с 2026-06-03):** из-за размера фаза разбита на три под-фазы, каждая со своей
> спекой/планом: **05a** PDU-кодек (`specs/2026-06-03-phase05a-iscsi-pdu-design.md`),
> **05b** SCSI-команды, **05c** сессия/транспорт (sans-I/O + tokio) + фейковый инициатор.
> Решения на всю фазу: sans-I/O ядро + тонкий async-адаптер; модуль `iscsi/` в `xboot-core`;
> стандартный подмножество RFC 7143; AuthMethod=None.

**Объём:**
- iSCSI login (security/operational negotiation — минимально необходимое для iPXE и Windows).
- Набор SCSI-команд: `INQUIRY`, `REPORT LUNS`, `READ CAPACITY (10/16)`, `TEST UNIT READY`,
  `READ (10/16)`, `WRITE (10/16)`, `SYNCHRONIZE CACHE`, минимальный `MODE SENSE`.
- Один **target на клиента**; в нём LUN'ы (LUN 0 = система; LUN 1.. = игры, добавляются здесь
  как механизм, реальное связывание — в фазе 07).
- Неподдержанные команды → корректный `CHECK CONDITION / Invalid Command` + лог, без падения.
- Команды чтения/записи проходят в `Volume` (через кэш).
- **Свой фейковый iSCSI-инициатор** в тестах (для интеграции без Windows).

**Зависимости:** 03 (Volume), 04 (кэш).

**Тестирование:**
- Юнит-тесты: побайтовая сборка/разбор iSCSI PDU и SCSI-ответов.
- `cargo-fuzz` на разборе входящих PDU.
- Интеграция с фейковым инициатором: полный цикл login → READ/WRITE → logout.
- Соответствие протоколу: реакция на неподдержанные команды, ошибки, обрыв сессии.
- Конкурентность: десятки виртуальных клиентов одновременно читают общий мастер и пишут
  каждый в свой оверлей; проверка изоляции и отсутствия гонок.

**Готово, когда:** фейковый инициатор полностью отрабатывает цикл; конкурентные клиенты
изолированы; фаззер PDU зелёный.

## Фаза 06 — Сетевая загрузка (proxyDHCP + TFTP + HTTP)

**Цель:** довести PXE-клиента от включения до момента подключения iSCSI-диска.

**Объём:**
- **proxyDHCP** — отвечает только на PXE-часть DHCP (не выдаёт IP), указывает на TFTP/HTTP;
  корректно сосуществует с существующим DHCP/роутером.
- **TFTP** — отдаёт готовый бинарник iPXE (UEFI и BIOS варианты).
- **HTTP** — отдаёт сгенерированный под конкретный MAC iPXE boot-скрипт (какой target
  подключить и грузиться).
- Абстракция `NetIo`: на Linux — raw-сокеты; на Windows — захват/инжект пакетов (Npcap) или
  сокеты. Платформенные реализации за трейтом.

**Зависимости:** 01 (`NetIo`, конфиг). От 02–05 не зависит (можно делать параллельно).

**Тестирование:**
- Юнит-тесты: сборка/разбор DHCP-PXE пакетов, корректный proxyDHCP-ответ.
- Юнит-тесты TFTP-протокола (RRQ, блоки, повторы).
- Тест генерации iPXE boot-скрипта по MAC из конфига.
- Локальный интеграционный прогон цепочки без реального железа (мок-клиент шлёт DHCP/TFTP/HTTP).

**Готово, когда:** мок-клиент проходит DHCP→TFTP→HTTP и получает корректный boot-скрипт,
указывающий на нужный iSCSI-target.

## Фаза 07 — Сборка и Disk/Client Manager

**Цель:** связать всё в работающий сервер: конфиг на входе → мульти-клиентская загрузка на выходе.

**Объём:**
- Disk/Client Manager: из конфига строит диски (image/game/writeback) с их RAM-бюджетами.
- На подключение клиента (по MAC): собрать один iSCSI-target с LUN'ами —
  `LUN0 = system (image + writeback-оверлей)`, `LUN1.. = games (game + writeback-оверлей)`.
- `client_defaults` для неизвестных MAC.
- Жизненный цикл сессии: подключение → выдача target → обрыв/ребут → **сброс volatile-оверлеев**
  клиента.
- Маршрут «boot-скрипт фазы 06 → target этого клиента».
- Игровой диск окончательно включается здесь как дополнительный LUN.

**Зависимости:** 05 (target/LUN'ы), 06 (boot-скрипт указывает на target), 03/04 (тома и кэш).

**Тестирование:**
- Интеграция: конфиг с несколькими дисками и клиентами → корректная сборка target'ов и LUN'ов.
- Сценарий жизненного цикла: клиент подключился → пописал в систему и в игры → ребут →
  оба оверлея сброшены → снова чистые мастера.
- `client_defaults`: неизвестный MAC получает дефолтный профиль.

**Готово, когда:** полный сервер из реального конфига отдаёт нескольким клиентам системный и
игровой LUN'ы, изолирует и сбрасывает их writeback'и.

## Фаза 08 — E2E на Windows + закалка

**Цель:** доказать, что реальный Windows грузится по сети, и довести v1 до релизного качества.

**Объём:**
- E2E-прогон: Windows-VM (QEMU/VirtualBox) грузится по сети с XBoot до рабочего рабочего стола;
  системный и игровой диск видны как локальные.
- Регрессионный набор: каждый найденный в E2E баг закрепляется автоматическим тестом.
- Ворота по покрытию (`tarpaulin`) на критичных модулях (COW, кэш, парсер, iSCSI).
- Документация: как подготовить мастер-VHD, как настроить конфиг, как запустить сервер.
- Прогон сервера на самой Windows (целевая ОС), не только на Linux.

**Зависимости:** 07 (полный сервер).

**Тестирование:** ручной/полуавтоматический E2E + весь автоматический набор фаз 01–07 зелёный.

**Готово, когда:** реальный Windows грузится бездисково с XBoot на нескольких клиентах; v1 готов.

## Что вне v1 (см. спеку §8)

Persistent writeback, веб-панель/API, захват образа с эталонной машины, раздача игр по SMB,
группы машин, автоматизированная подготовка Windows-образа (инжект iSCSI-boot, SAN policy).
Каждое — отдельный цикл спека → план → реализация после v1.
