# Phase 04 — Block Cache (общий RAM-кэш мастер-блоков)

**Дата:** 2026-06-03
**Фаза:** 04 (см. `docs/superpowers/plans/2026-06-02-xboot-roadmap.md`)
**Зависит от:** 02 (BackingStore — источник блоков), 03 (Volume — точка встройки на пути чтения)
**Главная спека:** `docs/superpowers/specs/2026-06-02-xboot-diskless-boot-engine-design.md` (§4 правило COW, §6 переполнение кэша)

## Цель

Один раз держать в RAM горячие блоки read-only мастера на всех клиентов одного диска и
никогда не превышать настроенный байтовый бюджет (`ram_cache` из конфига). Все клиенты
читают один и тот же мастер → блок кэшируется один раз на всех. Вытеснение — LRU в пределах
бюджета. Потокобезопасно: десятки клиентов читают конкурентно.

## 1. Компонент и его место

Новый модуль `crates/xboot-core/src/cache/` с типом **`CachedStore`** — декоратором,
реализующим трейт `BackingStore`. Он оборачивает внутренний `Box<dyn BackingStore>`
(настоящий мастер: VHD/VHDX/raw) и общий LRU-кэш блоков под `Mutex`.

```
Volume { master, overlay }
           │  master теперь = Arc<CachedStore> (через Arc-адаптер, как ArcStore в тестах volume)
           ▼
CachedStore { inner: Box<dyn BackingStore>, cache: Mutex<LruState>, hits, misses }
           │  на промахе
           ▼
inner.read_at(...)   // настоящий VHD/VHDX/raw
```

- `Volume` **не меняется** — ему по-прежнему передают `master: Box<dyn BackingStore>`,
  просто теперь это закэшированная обёртка.
- Один `Arc<CachedStore>` на диск-мастер шарится между всеми клиентами этого диска
  (несколько `Volume` держат клоны `Arc`; для передачи в `Box<dyn BackingStore>` используется
  тот же тонкий Arc-адаптер, что уже есть в тестах `volume`).
- Конструктор: `CachedStore::new(inner: Box<dyn BackingStore>, budget_bytes: u64) -> Self`.
- Размер блока — общая константа `BLOCK = 4096` (та же, что в `volume::overlay`;
  переиспользуем `crate::volume::BLOCK`, не плодим вторую константу).

## 2. Путь чтения (`read_at`)

Чтение идёт по блокам `BLOCK`, ровно как уже делает `Volume::read_at`:

- Для каждого блока `blk`, пересекающего запрошенный диапазон:
  - вычислить `block_len(blk)` = `min(BLOCK, size_bytes - blk*BLOCK)` (учёт короткого хвоста);
  - `lock → get(blk)`:
    - **hit** → инкремент `hits`, скопировать нужный под-диапазон блока в `buf`, отпустить lock;
    - **miss** → инкремент `misses`, **отпустить lock**, `inner.read_at(blk*BLOCK, &mut full)`
      читает **полный блок** длиной `block_len`, снова `lock`, вставить блок, отпустить,
      скопировать нужный под-диапазон в `buf`.
- Записи в кэш нет: мастер read-only (`BackingStore` не имеет метода записи), в кэш попадают
  только данные мастера.

## 3. Бюджет и вытеснение

`lru::LruCache<u64, Box<[u8]>>` создаётся **unbounded** (ограничение по числу элементов не
используется); байтовый бюджет ведём сами полем `current_bytes`.

- После вставки: `while current_bytes > budget { (_, v) = pop_lru(); current_bytes -= v.len() }`.
- **Инвариант бюджета:** после любой операции `current_bytes ≤ budget`.
- Блок вставляется в кэш только если `block_len ≤ budget`; иначе — **read-through**: данные
  отдаются из мастера, но в кэш не кладутся. Это покрывает оба граничных случая —
  `budget < BLOCK` и `budget == 0`. Поскольку вставляем только блоки `≤ budget`, цикл
  вытеснения гарантированно завершается, оставив только что вставленный блок.
- `current_bytes` считает суммарную длину хранимых блоков (включая короткий хвост по его
  фактической длине).

## 4. Конкурентность

- Один `Mutex<LruState>` на весь кэш диска. `RwLock` не подходит: `LruCache::get` требует
  `&mut self` (двигает элемент в MRU).
- Lock **не удерживается** во время дискового I/O: `lock → проверка → (miss) unlock → inner
  read → lock → insert`. Чтения разных блоков и разных клиентов идут параллельно.
- Допустимая гонка: два потока промахиваются по одному блоку и оба читают его из мастера —
  безопасно и идемпотентно (данные идентичны, последняя вставка побеждает; лишь редкая
  лишняя работа). Корректность данных не страдает.
- `CachedStore: Send + Sync`, шарится между клиентами как `Arc<CachedStore>`.

## 5. Статистика / наблюдаемость

Лёгкие счётчики внутри `CachedStore` — `hits: AtomicU64`, `misses: AtomicU64` (вне критической
секции мьютекса). Метод `stats() -> CacheStats { hits, misses, blocks, bytes }`, где `blocks`
и `bytes` берутся под lock из текущего состояния кэша. Нужен прежде всего тестам (проверять
hit/miss и что повторное чтение обслужено из кэша) и пригодится позже для логов/диагностики.
Никакой внешней системы метрик в v1.

## 6. Обработка ошибок

- `inner.read_at` вернул `Err` → пробрасываем как есть, **в кэш ничего не кладём** (не
  кэшируем ошибки/частичные данные). Состояние кэша остаётся согласованным.
- `Mutex` poisoning: внутренние `lock().unwrap()` — как в `RamOverlay`; отравление означает
  панику в другом потоке, это баг, а не штатная ситуация.
- Проверка границ (offset/len за пределами диска) не дублируется: `CachedStore` доверяет
  контракту `BackingStore::read_at`, а `Volume` уже проверяет границы выше по стеку.

## 7. Стратегия тестирования (TDD)

Юнит-тесты в `cache/mod.rs` поверх in-memory `Mem`-стора (как в `volume`):

- **hit/miss:** первое чтение блока — miss, повторное того же блока — hit (через `stats()`);
  содержимое совпадает с мастером.
- **read-through на нулевом/малом бюджете:** `budget == 0` и `budget < BLOCK` → данные верны,
  `stats().blocks == 0`, бюджет не превышен.
- **байт-корректность:** чтения с произвольных смещений/длин (пересечение границ блоков,
  короткий хвост) == прямое чтение из мастера.
- **бюджет:** заполнение сверх бюджета → `bytes ≤ budget` после каждого шага; число блоков
  соответствует ожидаемому.
- **порядок LRU:** доступ к старому блоку делает его «свежим» → при вытеснении уходит не он,
  а следующий по давности.
- **proptest (прозрачность + инвариант):** случайная последовательность чтений — `CachedStore`
  отдаёт ровно то же, что прямой `BackingStore`, и `bytes ≤ budget` ни разу не нарушается.
- **конкурентность:** N потоков параллельно читают один мастер через `Arc<CachedStore>` →
  данные корректны, инвариант бюджета держится.

Зависимость: добавить `lru` в `crates/xboot-core/Cargo.toml`.

## Готово, когда

Повторные чтения обслуживаются из кэша (растёт `hits`); `bytes ≤ budget` всегда; LRU корректен
под нагрузкой; `Volume` работает поверх `CachedStore` без изменений своего кода;
`cargo fmt --check`, `cargo clippy --all-targets --all-features -- -D warnings` и весь тест-сьют
(`cargo test --all`) зелёные.

## Вне области Phase 04

Кэш writeback-оверлея (у writeback-диска свой `ram_cache`, но это отдельная политика —
не входит сюда); шардирование мьютекса / lock-free кэш; вытеснение по числу элементов;
prefetch/readahead; персистентность кэша. При необходимости — отдельные циклы после v1.
