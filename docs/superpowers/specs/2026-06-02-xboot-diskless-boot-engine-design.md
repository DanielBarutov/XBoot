# XBoot — Диск­лес-загрузочный движок (v1) — Дизайн

**Дата:** 2026-06-02
**Статус:** утверждён к реализации
**Автор:** Daniel (barutovdg@gmail.com)

## 1. Что это и зачем

XBoot — open-source альтернатива CCboot: сервер бездисковой (diskless) загрузки. Клиентские
ПК грузятся по сети через PXE с центрального «золотого» образа на сервере; локальные диски
клиентам не нужны. Основной сценарий — игровой клуб: десятки одинаковых Windows-машин,
один мастер-образ ОС и общий большой диск с играми.

Цель проекта — долгоживущая open-source замена проприетарному CCboot, написанная на Rust.

### Не-цели (вне рамок v1)
- Веб-панель управления (в v1 — конфиг TOML).
- Persistent writeback (только volatile).
- Захват образа с эталонной машины по сети.
- Раздача игр по SMB (только iSCSI).
- Клиентские ОС кроме Windows.

## 2. Ключевые решения

| Решение | Выбор | Почему |
|---|---|---|
| Клиентская ОС | Только Windows (v1) | Классический сценарий клуба; самый сложный путь |
| Цель проекта | Open-source альтернатива CCboot | Долгая поддержка, сообщество |
| Scope v1 | Много клиентов + общий RAM-кэш | Сразу полезный движок, но без веб-UI |
| ОС сервера | Windows (прод), Linux (разработка) | Сервер раздаёт локальные игровые диски с Windows-хоста |
| Архитектура | Чистый Rust, один процесс, кросс-платформенный (tokio) | Windows-таргет исключает Linux-only LIO/device-mapper |
| Транспорт диска | Собственный iSCSI-таргет на Rust | Windows нативно грузится по iSCSI (через iBFT) |
| Структура target | Один iSCSI target на клиента, несколько LUN | Лучшая связность, проще клиенту |
| Writeback | Volatile (сброс при ребуте) | Классика клуба, простейшая реализация |
| DHCP | proxyDHCP рядом с существующим DHCP | Не ломает сеть, легко внедрить |
| Формат мастер-образа | VHD/VHDX | Удобно для Windows/Hyper-V workflow |
| iPXE | Готовые бинарники + chainload | iPXE не пишем, только встраиваем boot-скрипт |
| Игры | Отдельный общий iSCSI-диск (RO + writeback) | 3-4 ТБ игр невозможно держать в образе |
| Управление дисками | Диски — сущности первого класса с типами и RAM-бюджетом | Разделение ресурсов, гибкость хранения |

## 3. Архитектура

XBoot — один кросс-платформенный бинарник на Rust (async, tokio). Платформо-зависимые
куски (сеть на Windows vs Linux) изолированы за трейтами.

```
                    ┌─────────────────────────────────────────┐
                    │                XBoot (один процесс)       │
   PXE-клиент ─────►│  proxyDHCP ─► TFTP ─► (iPXE chainload)    │
   (UEFI/BIOS)      │       │                                   │
                    │       └─► HTTP (boot-скрипт, ассеты)      │
                    │                                           │
   iSCSI-инициатор─►│  iSCSI Target  ──►  Volume Manager        │
   (Windows ядро)   │   (login, SCSI)      │                    │
                    │                      ├─ Image volume (RO) │
                    │                      ├─ Game volume (RO)  │  ──► Backing
                    │                      └─ Writeback (COW)   │      stores
                    │                                           │      (VHD/VHDX,
                    │  Block Cache (RAM, бюджет на диск)        │       файлы, тома)
                    │  Disk/Client Manager  ◄── config (TOML)   │
                    └─────────────────────────────────────────┘
```

### Подсистемы

1. **Network boot**
   - **proxyDHCP** — отвечает только на PXE-часть DHCP-обмена (не выдаёт IP). Указывает
     клиенту, где взять загрузчик. Существующий роутер/DHCP продолжает раздавать IP.
   - **TFTP** — отдаёт бинарник iPXE (UEFI/BIOS варианты).
   - **HTTP** — отдаёт сгенерированный под конкретный MAC iPXE boot-скрипт и ассеты.

2. **iSCSI Target** — собственная реализация:
   - Фаза login (security/operational negotiation, минимально необходимое).
   - Набор SCSI-команд: `INQUIRY`, `REPORT LUNS`, `READ CAPACITY (10/16)`,
     `TEST UNIT READY`, `READ (10/16)`, `WRITE (10/16)`, `SYNCHRONIZE CACHE`,
     `MODE SENSE` (минимально). Неподдержанные → корректный `CHECK CONDITION`.
   - Один target на клиента; LUN 0 = system, LUN 1.. = game-тома.

3. **Volume Manager** — собирает виртуальный том клиента из backing store + COW-оверлея;
   реализует copy-on-write (см. §4).

4. **Block Cache** — общий RAM-кэш блоков read-only мастер-образов. Все клиенты читают одно
   и то же → кэшируется один раз на всех. Бюджет RAM настраивается **на каждый диск**;
   вытеснение LRU в пределах бюджета.

5. **Disk/Client Manager** — управляет дисками (типы Image/Game/Writeback) и клиентами
   (MAC → образ + тома + writeback-политика). В v1 — через TOML.

6. **Storage abstraction**
   - Трейт `BackingStore` (чтение/запись блоков); реализации: VHD, VHDX, raw-файл, сырой том.
   - Трейт `NetIo` — прячет платформенные различия сети (Windows захват пакетов / Linux raw-сокеты).
   - **Цепочки инкрементов CCBoot.** CCBoot хранит мастер-образ как базовый VHD + нумерованные
     инкременты (`name.vhd` + `name.001.vhd` … `name.00N.vhd`). Каждый инкремент — обычный
     *dynamic* VHD (disk type 3, не differencing): посекторный bitmap блока означает «сектор
     переопределён в этом слое», связь с родителем — только через имя файла. Чтение сектора:
     слой с наибольшим номером, где бит установлен, иначе — база. `open_backing` обнаруживает
     инкременты автоматически (регистронезависимо) и собирает `ChainedVhd`; без инкрементов
     поведение прежнее. Без этой склейки клиент получает устаревшие сектора (включая метаданные
     NTFS) и не загружается — именно так CCBoot-образ отличается от «просто VHD».

## 4. Поток данных: загрузка клиента

1. **Включение ПК** — в BIOS/UEFI выбрана сетевая загрузка; сетевая карта шлёт DHCP-запрос
   с PXE-пометкой.
2. **proxyDHCP отвечает** — роутер выдаёт IP, XBoot отвечает только PXE-частью: «загрузчик — у меня».
3. **TFTP отдаёт iPXE** — ПК скачивает загрузчик iPXE (умеет HTTP и iSCSI).
4. **iPXE просит boot-скрипт по HTTP** — XBoot отдаёт скрипт под конкретный MAC: какой iSCSI-таргет
   подключить и грузиться.
5. **iPXE подключает iSCSI-диск и передаёт эстафету Windows** — через таблицу iBFT ядро Windows
   видит системный диск «по сети», монтирует и стартует как обычный локальный диск.
6. **Чтение/запись Windows** идут в XBoot потоком SCSI-команд → в Volume Manager.

### Логика copy-on-write (ядро движка)

```
READ блока N:
    есть блок N в writeback-оверлее клиента?  ── да ──► отдать из writeback
                          │ нет
                          ▼
    есть блок N в RAM-кэше мастера? ── да ──► отдать из кэша
                          │ нет
                          ▼
    прочитать из мастер-образа, положить в RAM-кэш, отдать

WRITE блока N:
    записать в writeback-оверлей клиента (мастер НИКОГДА не меняется)
```

Следствия:
- Мастер-образ только читается → безопасно делить между всеми и кэшировать один раз.
- Запись у каждого своя (writeback-оверлей). Volatile → при ребуте оверлей выбрасывается.
- Игровой диск работает так же: общий RO мастер игр + writeback под сейвы/настройки.

## 5. Модель дисков и клиентов (конфиг TOML)

**Диск (Disk)** — управляемое хранилище с типом и бюджетом RAM:

```toml
[[disk]]
id        = "win11-master"
type      = "image"                  # image | game | writeback
backing   = "D:/xboot/win11.vhdx"
mode      = "readonly"
ram_cache = "8GB"

[[disk]]
id        = "games-main"
type      = "game"
backing   = "E:/games.vhdx"
mode      = "readonly"
ram_cache = "16GB"

[[disk]]
id        = "wb-nvme"
type      = "writeback"
backing   = "F:/xboot/writeback/"    # папка на NVMe под оверлеи
ram_cache = "4GB"
policy    = "volatile"               # сброс при ребуте клиента
```

**Клиент (Client)** — привязка по MAC:

```toml
[[client]]
mac        = "AA:BB:CC:DD:EE:01"
name       = "PC-01"
system     = "win11-master"          # LUN 0
games      = ["games-main"]          # LUN 1..
writeback  = "wb-nvme"

[client_defaults]                    # профиль для незнакомых MAC
system     = "win11-master"
games      = ["games-main"]
writeback  = "wb-nvme"
```

Логика связывания:
- Системный том = `image disk (RO)` + оверлей на `writeback disk`.
- Игровой том = `game disk (RO)` + свой оверлей на `writeback disk`.
- При загрузке XBoot собирает для MAC один iSCSI target: `LUN0 = system`, `LUN1.. = games`.
- Неизвестный MAC → `client_defaults`.
- RAM-кэши дисков независимы — игровой не вытесняет системный из памяти.

## 6. Обработка ошибок

- **Клиент отвалился/ребутнулся** — iSCSI-сессия рвётся; volatile-оверлей выбрасывается;
  следующая загрузка с чистого мастера.
- **Изоляция writeback** — оверлеи строго пер-клиент (ключ = MAC/сессия), физически разные
  файлы/области; конфликт невозможен по конструкции.
- **Backing store недоступен** — отказ в старте target'а с понятной ошибкой в лог; клиент
  видит «boot failed», а не мусор.
- **Неподдержанная SCSI-команда** — корректный `CHECK CONDITION / Invalid Command` + лог
  (видеть, чего не хватает реальному Windows), без падения.
- **RAM-кэш переполнен** — вытеснение LRU в пределах бюджета диска; не выходим за `ram_cache`.
- **Защита мастера** — мастер открывается строго read-only на уровне ОС; запись физически
  невозможна.

## 7. Стратегия тестирования

Цель: к первому «живому» прогону на Windows логика отлажена ~95% автоматикой; E2E ловит только
капризы реального железа.

**Слой 1 — Юнит-тесты (быстрые, на каждом сохранении):**
- COW-логика по каждой ветке (writeback→cache→master).
- LRU-кэш: вытеснение, бюджет, hits/misses, граничные размеры.
- Парсер VHD/VHDX: fixed/dynamic, BAT, метаданные, секторы.
- Сборка/разбор iSCSI PDU и SCSI-ответов (побайтово).

**Слой 2 — Property-based и fuzz:**
- `proptest`: случайная последовательность READ/WRITE на оверлей == эталонная in-memory модель.
- `cargo-fuzz` парсера VHD/VHDX и iSCSI PDU: мусор на входе не вызывает паник/крэшей.

**Слой 3 — Интеграция с фейковым инициатором (без Windows, в CI):**
- Минимальный собственный iSCSI-инициатор: login → READ/WRITE → logout.
- Соответствие протоколу: неподдержанные команды, ошибки, обрывы.
- Конкурентность: десятки виртуальных клиентов одновременно читают общий мастер и пишут
  каждый в свой writeback; проверка изоляции и отсутствия гонок (санитайзер).

**Слой 4 — Сценарные/регрессионные:**
- Golden-фикстуры: маленький заготовленный VHD → серия операций → сверка с эталоном.
- Жизненный цикл: подключился → пописал → ребут → writeback сброшен → чистый мастер.
- Каждый найденный баг закрепляется регресс-тестом.

**Слой 5 — E2E (последний, дорогой):**
- Реальный Windows в VM (QEMU/VirtualBox) грузится по сети с XBoot.

**Принципы:** TDD везде; покрытие (`tarpaulin`) измеряем на критичных модулях
(COW, кэш, парсер, iSCSI) и целимся в высокий процент именно там.
